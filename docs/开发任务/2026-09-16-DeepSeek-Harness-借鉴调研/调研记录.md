# DeepSeek Harness 实验性能力（Browser Use / Computer Use）借鉴调研

> **状态**：调研记录（仅供参考，未进入实施）
> **日期**：2026-09-16
> **目的**：对照 DeepSeek Harness v0.1.6-alpha.1 新增的两项实验性能力，评估当前项目 RPA 采集架构可借鉴的模式与取舍。
> **相关代码**：`apps/desktop/src/main/{chrome,agent-runtime,python-runner,collection-runner}.ts`、`skills/diantoushi-product-research/scripts/run_diantoushi_rpa_cdp.py`

---

## 1. 背景：DS Harness 的两项能力

DeepSeek Harness v0.1.6-alpha.1 同时新增**实验性**的 Browser Use 和 Computer Use，均需手动启用：

- **Browser Use**：模型可直接操作网页。支持
  - Playwright MCP
  - Chrome DevTools MCP
  - Stagehand
- **Computer Use**：模型可查看并控制本地桌面。接入 **Cua Driver**，可
  - 找到具体 App 和窗口
  - 获取当前界面截图
  - 根据**界面元素**或**坐标**执行点击和输入
  - 提供 **MCP** 和**原生**两种接入方式
- **Computer Use 前置条件**：需要给实际运行它的应用授予**屏幕读取**和**电脑操作**权限。

---

## 2. 关键认知：两种自动化模型的本质区别

DS Harness 的 Browser Use / Computer Use 本质是**通用、LLM 驱动的 Agent 操作原语**——**模型自己决定"看哪里、点什么、输入什么"**。

当前项目的"RPA 采集"是**预编排的专用采集器**——脚本写死"去店透视搜索 → 等加载 → 翻页 → 下载"，没有模型决策环节。

因此不能简单说"是否借鉴"，需拆成三层看：**驱动层（底层能力）、编排层、决策层**。

---

## 3. 当前项目现状对照

| 层 | 当前实现 | 对应 DS Harness | 差距 |
| :--- | :--- | :--- | :--- |
| **Chrome 控制** | `chrome.ts` 封装 CDP：`launchChromeForRpa`（headless/独立 profile + `DevToolsActivePort`）+ `evaluatePage`（WebSocket 执行 `Runtime.evaluate`）+ `closeChrome` | **Browser Use** 的基础 | 已是通用雏形，但只有 `Runtime.evaluate` 一个口子，非全量 CDP 封装 |
| **网页采集** | `run_diantoushi_rpa_cdp.py` 用 Playwright/CDP 连接已开 Chrome，硬编码店透视操作流 | Browser Use 的 MCP（Playwright MCP / Chrome DevTools MCP） | **专用 vs 通用**：当前脚本是"这一个平台、这一套点击"写死，不通用 |
| **任务编排** | `collection-runner.ts`：download→collect-files→import→sync 阶段化；`collection-modes.ts` 白名单/模式校验 | 无直接对应 | 属业务流水线，非 Agent 能力 |
| **"Agent"运行时** | `agent-runtime.ts`：**单任务互斥的 Python 子进程运行器**（start/cancel/cleanup），名字叫 Agent 但**没有 LLM 决策** | `packages/host` + LLM 决策循环 | 差距最大：当前是"进程调度器"，DS 是"带规划的 Agent" |
| **桌面控制 (Computer Use)** | **完全没有**——无截图、无 `desktopCapturer`、无元素定位、无坐标点击（已 grep 确认） | **Computer Use**（Cua Driver） | 当前项目为空白 |

### 当前项目已有的事实定位

- **Browser Use 第 0 层（CDP 驱动）已就位**：有独立的 Chrome 进程生命周期管理、可复用 profile、基于 `DevToolsActivePort` 的端口发现、WebSocket 的 evaluate 通道。
- **无 Computer Use 相关能力**：源码中无桌面截图/桌面控制残留（仅命中生成的 Prisma 库代码样板）。
- **安全底子是"原生受限入口"**：Electron 走 `contextIsolation:true`、`sandbox:true`、`nodeIntegration:false` 的受限 preload 桥——这本身就是 DS"原生接入方式"的正确姿势，与桌面权限控制能力天然冲突（见 §5.3）。

## 4. 值得借鉴的点（按性价比排序）

### 4.1 值得做：把 `chrome.ts` 升级为"可注入的通用 Browser 驱动接口"

当前 `evaluatePage` 暴露的 `Runtime.evaluate`（执行任意 JS）其实已够通用，但定位是"给店透视脚本用"，不是"给任意 Agent 用"。DS 的做法是把它封装成 **MCP 工具**（`browser_click` / `browser_type` / `browser_screenshot` 等语义化动作）。

**收益**：向上层（无论人还是模型）提供统一、按语义调用的驱动接口，新采集平台（拼多多、抖音、1688）复用一个驱动，无需每个平台重写一套 CDP 点击。这是低成本的地基升级。

### 4.2 值得借鉴：Agent 状态机与可中断性/可恢复

现有 `collection-modes.ts`（模式白名单）+ `collection-runner.ts`（阶段计划 + 事件落库 `localJobEvent`）这套"计划-执行-记录-可恢复"骨架方向正确，与 DS 的 `schedule`/`workflow` 理念一致。

**缺口**：checkpoint / 重试 / 分支决策（DS 有 `job`、`goal`、`workflow` 包支撑）。若未来要支持"采集失败自动重试 / 验证码处暂停等人工"，可借鉴 DS 把"执行计划"从**代码**提升为**数据驱动的阶段列表 + 每阶段判据**。

### 4.3 可借鉴但非当务之急：MCP 化 / 双接入方式

DS 提供 MCP + 原生两种接入。当前 preload 桥本质已是"原生受限入口"。若将来希望让通用 Agent 客户端（如赖于大模型的外部 Agent）直接调用本地采集能力，可再按 MCP 暴露一组**只读采集工具**——属"开放能力"范畴，非产品 MVP 需要。

### 4.4 明确不建议现在做：Computer Use（桌面控制）

- DS 明确标注为**实验性**、需手动启用，且**必须给应用授予屏幕读取与电脑操作权限**。
- 当前产品（电商竞品采集）核心是**网页自动化**，用 Browser Use 就够。
- 桌面控制引入**大得多的权限面与安全风险**（能控制用户桌面 ≈ 能拿到整个电脑），与采集业务无直接关联。
- 除非未来有"操作非浏览器桌面软件"的硬需求，否则属过度设计。

## 5. 设计边界与风险提示

### 5.1 不破坏确定性采集的可靠性

当前脚本化采集（固定 CDP 操作流 + `GUARD_TERMS` 看门词 + 失败判据）是**确定性、可复现**的数据采集默认路径，应作为可靠基线保留。实验性的"模型驱动/图像定位"路径应隔离，不能打断主采集链路。

### 5.2 Liskov 式扩展而非推翻

借鉴方向是"在现有 CDP 地基上增加**通用语义化工具层**与**可选的状态机决策层**"，而非用 vision+agentic 模型替换掉脚本化采集器。两者是渐进可共存的关系。

### 5.3 权限/安全面权衡

Computer Use 所需的系统级屏幕读取 + 电脑操作权限，与当前 Electron 的
`sandbox:true`、`nodeIntegration:false` 受限入口存在**结构性张力**。引入前必须先明确：给哪个进程/模块授权、授权边界多大、如何最小化。在业务上无刚需前，保持不开。

### 5.4 关于"借鉴"的两点纠偏

- 当前 Node CDP 实现是**自研 WebSocket 通道**；DS Browser Use 走 Playwright MCP / Chrome DevTools MCP / Stagehand。可参考的是"语义化封装 + 统一错误/超时/重试"的**接口设计**，而非必须迁移到 MCP Server。
- 采集侧已 `python` 侧用 Playwright 连已开 Chrome；这与 DS 的 Playwright 用法同源，未来如需更健壮的页面操作，可在 Python 侧沿用 Playwright 而非自持 CDP WebSocket。

---

## 6. 一句话结论

> 当前项目已踩在 **Browser Use 的地基** 上（CDP 驱动 + 阶段化编排 + 受限 preload 桥），缺 **通用化** 与 **决策层** 两环。
> 最该借鉴的是 DS **把网页操作封装成语义化通用工具 + Agent 状态机**，让采集从"单平台脚本"走向"可复用的多平台采集 Agent"；
> **Computer Use** 属另一条更大权限面、与当前业务关联弱的能力，**不建议现在引入**。
