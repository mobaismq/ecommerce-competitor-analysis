# 03 组件与依赖复用规范

## 1. 铁律：先复用，后引入

**项目里已有的技术库、组件、工具函数，必须优先使用，禁止重复造轮子；引入新依赖是例外而非默认。**

给 AI 的执行顺序：

1. 查本文档映射表 → 2. 查对应 `package.json` 的 dependencies → 3. 在现有页面/组件里搜同类实现（Arco 组件怎么用、请求怎么发、状态怎么存），照现有写法写 → 4. 确实没有现成的，才允许引入新依赖，并**向用户说明理由**。

## 2. 「要做什么 → 用什么现成的」映射表

### 渲染层（desktop/renderer）

| 要做的事 | 用现有的 | 禁止/不要 |
|---|---|---|
| 表格、表单、弹窗、抽屉、上传、日期选择等一切 UI | **Arco Design React**（`@arco-design/web-react`） | 不引入 antd、MUI、element 等第二组件库 |
| 快速样式/布局 | **Tailwind CSS 4** + Arco | 不引入 styled-components、CSS Modules 新范式 |
| 图标 | **lucide-react**（组件内）/ Arco Icon | 不再引入新图标库 |
| 列表动画、过渡 | **motion** | |
| 服务端数据获取/缓存/轮询 | **@tanstack/react-query** | 不要手写 useEffect + setState 拉数据 |
| 全局客户端状态 | **zustand**（`renderer/src/store/`） | 不引入 redux/mobx |
| 路由 | **react-router-dom 7** | |
| HTTP 请求（账户侧） | `renderer/src/api/` 现有封装（axios） | 不要裸写 fetch/新 axios 实例 |
| 业务数据读写 | preload IPC（`window` 上暴露的 API）→ worker 能力 | **不要**在渲染层直连 SQLite/文件系统/自建 HTTP |
| 日期时间 | **dayjs** | 不引入 moment |
| 工具函数 | **lodash-es**；没有的先看 `renderer/src/utils/` | |
| ID 生成 | **nanoid** | |
| 文件下载/导出 | **file-saver**（现有用法照抄） | |
| 消息提示/确认 | Arco 的 Message / Modal.confirm | 不要自研 toast |

### 主进程 / worker（desktop）

| 要做的事 | 用现有的 |
|---|---|
| 新增业务能力 | 仿照 `src/worker/*-capability.ts` 现有结构：protocol.ts 定义通道 → capability 实现 → main/capability-handlers.ts 注册 |
| 本地数据访问 | worker 内 Prisma（`worker-db.ts`），复用 desktop schema |
| 文件/图资产落盘 | StorageDriver 抽象（默认 local），不要私造路径写盘 |
| AI 调用（文本/生图/视觉） | `worker/ai-provider.ts` 现有供应商路由与密钥体系（个人自配 → 系统默认 → 诚实报错） |
| RPA/采集运行时 | `main/chrome.ts`（CDP）、`main/python-runner.ts`、`skills/` 技能 |
| 日志 | electron-log（`main/logger.ts`），密钥自动脱敏 |
| 持久化小配置 | electron-store（`main/store.ts`） |

### 服务端（backend）

| 要做的事 | 用现有的 |
|---|---|
| 新模块 | NestJS module/controller/service/dto 结构，参照现有模块（如 products、reports） |
| 参数校验/转换 | class-validator + class-transformer（全局管道已配） |
| 数据库访问 | Prisma（`prisma.service.ts`），勿引入其他 ORM/裸 SQL |
| 队列/任务 | `jobs/`、`queue/` 现有内嵌调度器 |
| 日志 | pino（nestjs-pino），勿 console.log 散落 |
| 鉴权 | 现有 JWT guard（`auth/`）与权限体系 |

### 测试

| 端 | 框架 | 注意 |
|---|---|---|
| desktop | vitest | worker 能力有契约 spec（如 worker-manager.spec），改 IPC 必须同步维护 |
| backend | jest（--runInBand） | 涉及 RPA/大模型的测试用离线样本或 Mock，禁止真实调用 |

## 3. 确需引入新依赖时的流程

1. **先确认没有替代**：在映射表、两个 app 的 `package.json`、`renderer/src/components|utils` 里找过。
2. **装对地方**：渲染层/主进程用的装 `apps/desktop`，服务端用的装 `apps/backend`；只有构建工具类才考虑根目录。不装 `apps/legacy`。
3. **说明理由**：告诉用户「现有 X 无法满足 Y，所以引入 Z」。
4. **过门禁**：`pnpm typecheck` + 相关单测通过后再交付。

## 4. 其他禁止事项

- 禁止在渲染层私造业务字段或判定逻辑（唯一权威判据铁律，见 04 号文档）。
- 禁止绕过 worker IPC 直接在渲染层做本地 IO / AI 调用 / 爬虫。
- 禁止把真实密钥写进任何被 git 跟踪的文件；`.env.example` 只放占位符。
- 禁止在 `apps/legacy/` 新增或修改代码。
